# 架构设计题 · 第 6 题：滑动窗口限流

> 设计一个接口限流器：按 `userId` 限流，任意连续 `windowSeconds` 秒内每个用户最多 `limit` 次请求，提供 `bool allow(String userId)`，必须是滑动窗口（非固定窗口），且不活跃用户的数据要能被清理。

---

## 一、单机实现：数据结构与核心逻辑

### 数据结构选择

采用 **`HashMap<userId, Deque<timestamp>>`**：

- 外层 `dict`：以 `userId` 为 key，索引到该用户的请求时间戳队列；
- 内层 `deque`：按时间**单调递增**存放请求时间戳，队首最旧、队尾最新。

选 `deque` 而非普通 `list` 的原因：两端 `popleft`/`append` 都是 O(1)，非常适合"从头部淘汰过期、从尾部追加新请求"的模式。

### 核心代码（Python）

```python
from collections import deque
import time


class SlidingWindowRateLimiter:
    def __init__(self, window_seconds: float, limit: int):
        assert window_seconds > 0 and limit > 0
        self.window = window_seconds
        self.limit = limit
        self._buckets: dict[str, deque] = {}

    def allow(self, user_id: str) -> bool:
        now = time.monotonic()  # 用单调时钟，抗系统时间跳变

        q = self._buckets.get(user_id)
        if q is None:
            q = deque()
            self._buckets[user_id] = q

        # 1. 淘汰窗口外的旧时间戳（窗口 = (now - window, now]）
        while q and now - q[0] >= self.window:
            q.popleft()

        # 2. 判断当前窗口内请求数
        if len(q) < self.limit:
            q.append(now)
            return True
        return False
```

### 关键点说明

1. **滑动窗口语义**：窗口左边界随当前时间实时滑动（`now - window`），因此是"任意连续 windowSeconds 内最多 limit 次"，而不是固定窗口的"按整点/整段计数"。这是它与固定窗口的本质区别。
2. **边界条件**：`now - q[0] >= window` 表示时间戳恰好在窗口左边界上时也算过期（左开右闭区间），避免同一时刻重复计数。
3. **单调时钟**：用 `time.monotonic()` 而非 `time.time()`。墙钟可能因 NTP 校时/手动改时间发生跳变，导致窗口计算错乱；单调时钟只增不减，更适合做时间间隔判断。

---

## 二、时间、空间复杂度

**时间复杂度：均摊 O(1)**

- 每个时间戳**入队一次、出队一次**，平摊到每次 `allow` 调用上是常数；
- 单次调用最坏可能弹出 k 个过期元素，但总弹出次数 ≤ 总入队次数，故均摊 O(1)。

**空间复杂度：O(活跃用户数 × limit)**

- 每个活跃用户最多保留 `limit` 个时间戳；
- 已超过窗口的旧时间戳会被立即淘汰，队列长度天然受 `limit` 约束。

---

## 三、不活跃用户的数据清理

目标：避免 `self._buckets` 只增不减导致内存泄漏。采用**三层策略**：

1. **惰性删除（主）**：`allow` 淘汰过期时间戳后，若队列为空，直接 `del self._buckets[user_id]`，让"刚好用完窗口"的用户立即释放内存。

```python
        while q and now - q[0] >= self.window:
            q.popleft()
        if not q and user_id in self._buckets:
            del self._buckets[user_id]
```

2. **定期扫描（兜底）**：后台线程每隔 `cleanup_interval` 秒扫描一次，删除"最后活跃时间早于阈值"的用户（需额外记录 `last_seen`）。适合长时间不来的用户。

3. **容量上限保护（防爆）**：当 `len(self._buckets)` 超过 `max_users` 时，驱逐最久未活跃的用户（可用 `OrderedDict` 实现近似 LRU），防止恶意大量 userID 撑爆内存。

三者组合即可覆盖"正常过期 / 长尾不活跃 / 恶意海量 key"三类情况。

## 四、四种限流算法对比

| 算法 | 原理 | 优点 | 缺点 | 典型场景 |
|---|---|---|---|---|
| **固定窗口** | 把时间切成固定段，段内计数 | 实现最简单、内存 O(1) | **临界突刺**：窗口交界处可能出现 2 倍流量 | 粗粒度、对精度不敏感的计数型限流 |
| **滑动窗口** | 任意连续窗口内计数（本题） | 平滑、精确，无突刺 | 需存时间戳，内存 O(limit) | 精确控制任意连续时间段的 API/接口限流 |
| **令牌桶** | 以固定速率放令牌，请求需取令牌 | 允许一定突发（桶容量）、平滑 | 实现与调参稍复杂 | 允许瞬时突发的场景：网关、下载、秒杀 |
| **漏桶** | 请求进桶，以固定速率流出 | 输出速率恒定、削峰填谷 | 完全抹平突发，突发请求排队 | 需严格恒定速率：消息消费、音视频流 |

**补充：固定窗口的"临界突刺"问题**

假设窗口 1 秒、限流 100 次。若在 `[0.99s, 1.00s]` 内来了 100 次、`[1.00s, 1.01s]` 内又来 100 次，两个"固定窗口"各自都没超限，但实际在 `[0.99s, 1.01s]` 这 20ms 内承受了 200 次请求——这就是固定窗口的缺陷，也是本题明确要求滑动窗口的原因。

**滑动窗口 vs 令牌桶**：滑动窗口对"任意连续时间段"的约束是**硬性精确**的；令牌桶的"突发"取决于桶容量，本质上放宽了短时间内的瞬时限制。若业务要求严格"任意 windowSeconds 内 ≤ limit 次"，滑动窗口更合适；若允许少量突发换取体验，令牌桶更友好。

## 五、Redis 集群限流设计

单机版只保证单进程内正确；多机/分布式必须把"窗口状态"集中到 Redis，并保证**判定 + 更新原子**。

### 1. Key 设计

```
key = "ratelimit:{userId}"
```

按 userId 分 key，天然隔离不同用户；可加业务前缀区分不同接口（如 `ratelimit:login:{userId}`）。

### 2. 数据结构：ZSET（有序集合）

| 字段 | 值 |
|---|---|
| key | `ratelimit:{userId}` |
| member | 请求唯一标识（时间戳 + 随机数/UUID），保证唯一不覆盖 |
| score | 请求发生的毫秒时间戳 |

选 ZSET 的原因：
- `score` 存时间戳，`ZREMRANGEBYSCORE` 可**一次删除窗口外所有旧记录**（O(log N)）；
- `ZCARD` 取窗口内数量 O(1)；
- `ZADD` 追加新记录 O(log N)。

### 3. 原子操作：Lua 脚本

Redis 单线程内执行 Lua 脚本天然原子，把"删过期 → 计数 → 判定 → 写入"串成一个不可分割的操作：

```lua
-- KEYS[1] = ratelimit key
-- ARGV[1] = windowMillis（窗口长度，毫秒）
-- ARGV[2] = limit
-- ARGV[3] = nowMillis（当前时间，毫秒）
-- ARGV[4] = member（请求唯一 ID）

-- 1. 删除窗口外的旧记录（score < now - window）
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', ARGV[3] - ARGV[1])

-- 2. 当前窗口内数量
local count = redis.call('ZCARD', KEYS[1])

-- 3. 判定 + 更新（原子）
if count < tonumber(ARGV[2]) then
    redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4])
    -- 设置过期时间 = 窗口长度，不活跃用户 key 自动回收
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
    return 1  -- 放行
else
    return 0  -- 拒绝
end
```

调用方（伪代码）：

```python
member = f"{now_nano}-{uuid4().hex}"  # 保证同毫秒多次请求不覆盖
allow = redis.eval(LUA, 1, key,
                   window_ms, limit, now_ms, member)
```

### 4. 三个必须注意的点

1. **member 唯一性**：若用"毫秒时间戳"做 member，同一毫秒内的多次请求会互相覆盖导致计数偏少。必须加随机后缀/UUID 保证唯一。

2. **过期时间 = 窗口长度**：`PEXPIRE key windowMillis` 让 key 在最后一个请求之后最多存活一个窗口周期，**自动清理不活跃用户**，无需额外扫描任务——这正好对应题目"不活跃用户数据要能清理"的要求。

3. **时间来源**：多机场景下各机器时钟可能不一致，`nowMillis` 应统一**由 Redis 服务器生成**（`redis.call('TIME')`），避免客户端时钟漂移导致窗口错乱：

```lua
local t = redis.call('TIME')  -- 返回 {秒, 微秒}
local now = t[1] * 1000 + math.floor(t[2] / 1000)
```

## 六、小结

| 维度 | 单机 | 多机（Redis） |
|---|---|---|
| 数据结构 | `dict[userId] -> deque` | `ZSET`（score=时间戳） |
| 判定逻辑 | 淘汰队首过期 → 比较长度 | Lua：删过期 → ZCARD → ZADD |
| 原子性 | 单线程天然保证 | Lua 脚本原子执行 |
| 复杂度 | 均摊 O(1) | O(log N)（ZSET 操作） |
| 不活跃清理 | 惰性删除 + 定期扫描 | PEXPIRE 自动过期 |

核心思想一句话：**滑动窗口 = 保留窗口内的时间戳序列，实时淘汰窗口外的旧值；分布式只是把这份序列搬进 Redis 并用 Lua 保证"判 + 写"原子。**
